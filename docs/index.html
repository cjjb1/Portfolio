Flujo de Vida de una Petición Documental (pdfDoc)

Secuencia & Pipeline
1
1. Petición Entrante NTLM / API Key
Validación de identidad en Active Directory o mediante token SHA-256 en cabecera X-API-Key hacia Master HTTP (:3000).
2
2. Smart Proxy & Enrutamiento Hit / Miss
Inspección de disco: si el PDF ya está cacheado, deriva en Round-Robin a Cache Workers (:5002+). Si no, enruta a SOAP Worker (:5001).
3
3. Adquisición Buffer SOAP DownloadFileAsync
Descarga asíncrona con ticket único desde MyDoc legacy (RC03), guardando el PDF en disco local y los metadatos en MariaDB.
4
4. Comprobación SYSESTADO Cola Tedious
Consulta serializada en MSSQL. Si el documento no está activo (SYSESTADO != 1), busca automáticamente sustituto con el mismo código de barras.
5
5. Estampado al Vuelo pdf-lib & bwip-js
Inyección dinámica sobre el buffer: sellos/overlays según estado (EST_XX.pdf), código de barras Code 128, fechas, comentarios y pie pericial AD.
6
6. Entrega Streaming & Auditoría HTTP 200
Streaming directo del PDF estampado hacia el navegador y registro del evento en la tabla expedientes_visualizacion.

Reglas Críticas de Concurrencia & Resiliencia Operativa

Alta Disponibilidad
🎫 Ticket SOAP Único

Solo 1 worker atiende peticiones SOAP para evitar colisiones de sesión y tickets concurrentes con el servicio legacy MyDoc.

🚦 Cola Serializada Tedious

SQL Server no admite peticiones concurrentes por el mismo socket; la cola adQueryQueue serializa todas las consultas garantizando integridad.

⏸️ Trabajador de Fondo con Backoff

El bucle asíncrono alterna precarga y limpieza solo cuando hay inactividad de usuario, pausándose inmediatamente ante tráfico web.

🪵 Logs Pino sin Colisión

Registro unificado con Pino mediante rotación por fecha directa (append) y compresión semanal desatendida centralizada en el Master.

Node.js Cluster Express 5 MariaDB MSSQL Tedious AS/400 DB2 ODBC UTF-8 NTLM SSO pdf-lib & bwip-js

Aspectos Técnicos Clave:

  • Arquitectura Master/Cluster Multi-Worker (cluster.mjs): Master HTTP centralizado con autenticación NTLM Active Directory y bypass con X-API-Key. Enrutamiento inteligente: 1 único SOAP Worker aislado (evitando colisión de tickets concurrentes con el sistema legacy) y N Cache Workers en Round-Robin para lectura, APIs y UI.
  • Estampado al vuelo y manipulación PDF (pdf-lib & bwip-js): Inyección dinámica sobre el documento de sellos según estado (EST_XX.pdf), códigos de barras Code 128, fechas de previsión, comentarios y pie de página de auditoría forense (usuario AD solicitante, workstation y timestamp).
  • Conector ERP AS/400 e ingesta desatendida EDM (conectorEdm.mjs): Cliente ODBC persistente en UTF-8 (CCSID=1208) con reconexión automática y mutex serializado. Resuelve en tiempo real pedidos de compras, proveedores y materiales tras el escaneo de albaranes de entrada de material.
  • Resiliencia, réplica y cola serializada Tedious (server.mjs): Doble persistencia relacional con catálogo y permisos en MariaDB (ivido/diso) para contingencia offline y cola asíncrona serializada adQueryQueue para garantizar la integridad en consultas MSSQL.
  • Bucle de fondo con backoff y retención documental: Tareas asíncronas de precarga en goteo y limpieza que se pausan de forma reactiva ante tráfico web de usuarios, integrando motor de expiración y retención documental por plazos auditados.

Arquitectura de Datos, Protocolos & Integración
PowerShell 5.1 IBM i PC5250 HLLAPI 32-bit Outlook MAPI Windows DPAPI

Aspectos Técnicos Clave:

  • Interacción nativa 5250 vía HLLAPI (pcshll32.dll): Automatiza la pantalla verde de IBM i emulada con máxima velocidad, gestionando credenciales cifradas con Windows DPAPI.
  • Triaje inteligente de correo (Outlook MAPI): Escaneo continuo cada 60s con regex de OTs y lógica anti-duplicidad para detectar si un técnico de IT ya intervino.
  • Sesión aislada multi-pantalla: Localiza letras de sesión libres (B a H) y opera en segundo plano minimizado sin interferir en los emuladores abiertos de los operarios.
  • Borrado inverso y seguro de pliegos: Verifica el estado 'Activo' de los encargos y realiza la purga en orden inverso con confirmación controlada ('J') antes de anular la OT principal.
  • Cierre higiénico y auditoría: Notificación automática vía ReplyAll manteniendo el hilo y liberando la sesión (6xF3 + Opción 24) para no consumir licencias del mainframe.
